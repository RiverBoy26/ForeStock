# Техническая архитектура для команды разработки

## Роли сервисов

```text
External data sources (sales/stock/catalog)
    -> ingestion -> validation -> warehouse / versioned feature-store
    -> scheduled ML training & walk-forward evaluation -> model registry
    -> Python inference (LightGBM v7.4) -> versioned forecast artifacts
    -> Java Spring Boot business backend -> REST / frontend / reporting
                       ^
                   monitoring & access control
```

**В ZIP реализовано:** сохранённая обученная модель, исторический snapshot, готовые CSV, inference CLI, read-only FastAPI, модельный манифест, валидация, тесты, Docker. **В ZIP не реализовано:** ваши источники ETL, БД, аутентификация пользователей, webhook-уведомления, регламент обновления, пайплайн тренировки в Kubernetes, управление доступом и мониторинг. Их строят разработчики.

## Feature engineering / online vs batch

- **Base 39 моделей:** global Tweedie, global Poisson, складские Tweedie, склад×категория Tweedie, recursive Tweedie и recursive Poisson. Правило fallback: склад → global Tweedie, склад×категория → склад. M5-lite — равновесная смесь шести прогнозов. Базовый `hybrid_raw = 0.5 * global_tweedie + 0.5 * m5lite`.
- **META 2 модели:** вероятность `P(qty>0)` и `E[log(1+qty)|qty>0]` (преобразуем обратно `expm1`). Используются лаги, продажи за 4/13/26/52 недель, склад, категории, остатки, горизонт, сырой прогноз и различие моделей.
- **Selected:** при P>=0.55 прогноз минимум 1.0; при P<0.55 ставится 0. Коррекция исходного объёма по conditional-регрессии с `alpha=0.15`, если за последние 13 недель были продажи в >=7 неделях. Отношение ограничено [0.65;1.6].
- **Фиксированный cutoff:** факты до 26.07.2026 включительно; прогноз 27.07.2026–27.09.2026 на недельных интервалах. Нельзя задним числом добавлять 27–31 июля из исходного архива.
- **Нумерация категорий/складов:** кодирована от конкретного обучающего датасета; **переупорядочивание справочников ломает предсказания**. Snapshot удерживает тот же порядок, а `schema.json` фиксирует имена 116 признаков.
- **Stock:** все дубли дневных остатков по складу/артикулу суммируются; snapshot хранит агрегаты, а не исходные строки.
- **Новые товары/склады:** текущая артефактная модель фиксирует 11 складов, 799 артикулов; неизвестные ключи не поддерживаются и требуют расширения ETL и обучения.

## Контракт HTTP

- `GET /healthz` — liveness.
- `GET /readyz` — availability данных (не доказывает качество модели).
- `GET /v1/model` — дата cutoff, период, варианты и размерность.
- `GET /v1/forecasts?variant=selected&week=2026-07-27&warehouse_name=...&article=...&limit=100&offset=0` — JSON с `total, offset, limit, items[]`.
- `GET /v1/export/selected.csv` (или conservative/smape_experimental/baseline) — полная выгрузка CSV.
- При наличии `NONTON_API_KEY` все `/v1/*` требуют `X-API-Key`; это сервис-сервис ключ, **не** пользовательская авторизация.
- `GET /docs` — OpenAPI. Полная спецификация экспортирована в `docs/openapi.json`.

Ответ (схема):
```json
{"variant":"selected","total":1,"offset":0,"limit":100,
 "items":[{"week":"2026-07-27","warehouse_name":"<warehouse>","article":"<article>","quantity":1.75}]}
```

## Контракт прогнозов

Файлы имеют поля: `week` (`YYYY-MM-DD`, понедельник), `warehouse_name` (строка, точное исходное значение), `article` (строка, точное исходное значение), `quantity` (неотрицательный float, **прогноз**, не факт).

Нет подтверждения, что официальная система принимает другие измерения; поэтому ничего не менять в ключах без согласования. Формат: 79 101 строка = 11×799×9, один ключ `(week, warehouse_name, article)` на строку.

## План боевого внедрения (работа разработчиков)

1. Интегрировать загрузку продаж/остатков и тесты корректности агрегаций в ingestion.
2. Версионировать справочники, полный feature snapshot и целевые девятинедельные окна, исключать будущие события относительно cutoff.
3. CI: тесты схемы, сравнение golden-прогнозов, код/версия моделей, контроль утечек, регрессионные проверки.
4. Для каждой новой даты — retrain и walk-forward в отдельном job, регистрация новой версии artifacts, продуманная canary/rollback стратегия.
5. Java backend ходит в Python API по приватной сети либо импортирует готовый CSV в свою PostgreSQL (для текущего конкурса этого достаточно и проще).
6. Доступ к агрегированной истории в snapshot ограничить; шифровать диски/бэкапы и не добавлять snapshot в публичный Git.

**Важная граница:** зафиксированный inference с этим snapshot воспроизводит только конкурсные девять недель. Здесь НЕТ API, который может корректно прогнозировать произвольную неделю в 2027 году, не обновив историю и не переобучив модель.
