# Аудит динамического прогнозирования ForeStock

Дата аудита: 31.10.2026. Текущая ветка: `develop`.

## Вывод

В репозитории уже есть путь загрузки двух CSV и расчёта прогнозов через Python API, Java backend и серверный HTML frontend. Python путь использует **Nonton v7.4** (`ml-service/models`), а не Signature v8.1 и не MOE. Он пересобирает rolling features для известных ключей с помощью загруженных фактов и затем запускает сохранённые v7.4 LightGBM. Это не доказывает совместимость произвольного CSV, неизвестных ключей или другой даты.

Поставленная цель Signature v8.1 пока **не выполнена**. API не принимает `model_version`, не запускает job-очередь, не выдаёт summary/pagination, а UI — Spring MVC + Thymeleaf, не React. Не пройдены golden, data-dependence, leakage и интеграционные критерии из задания. Внешние данные для golden test отсутствуют: в `D:\datasets\df40-fake` находится только файл задания, оригинального `hakaton.zip` там нет.

Чтобы исключить тихое смещение календарных и `origin_index` признаков текущей v7.4, endpoint теперь допускает только cutoff `2026-07-26` (воскресенье). Если cutoff не передан, он определяется по последнему воскресенью, покрытому обоими файлами; если это не конкурсная дата, запрос отклоняется с `MODEL_OUT_OF_DOMAIN` и HTTP 422. Данные после фиксированного cutoff исключаются из rolling окна существующей логикой.

## Что реально хранится в пакетах

### Текущий `ml-service` (Nonton v7.4)

- `models/base/schema.json` сохраняет имена и порядок 116 признаков, включая 5 categorical ID.
- `snapshots/weekly_history_2026-07-26.npz` сохраняет фиксированную сетку 11 складов × 799 артикулов, их числовые ID, таблицы категорий товара, bucket-справочники департаментов/городов и агрегированные ряды за 134 недели. `snapshot.load_dataset` намеренно проверяет ровно эту сетку и временной диапазон.
- 39 LightGBM и две META-модели находятся в `models/`; формат и SHA-256 фиксируются `model_manifest.json`.
- Внешний CSV может обновить временные значения только для идентификаторов, уже присутствующих в snapshot. Новый `sorted(unique(upload))` не используется; неизвестные склад или артикул отклоняются.
- Окно и единственный безопасно подтверждённый origin — конкурсный cutoff. Перенос календаря, `FINAL`, сезонных полей и рекурсивной истории на новую дату не проверен.
- Источник агрегированных числовых ID и точные словари — snapshot; отдельной полной таблицы соответствий категорий для новых значений нет. Неизвестные bucket-значения в текущем rolling builder попадают в `__OTHER__`, что само по себе не доказывает корректность для новых доменов.

### Signature v8.1 (соседний пакет в репозитории)

- Сохранены 39 LightGBM и два CatBoost, 116-полевая схема базовых моделей и схема финальных CatBoost в `docs/model_schema.json` (62 поля), включая категориальные столбцы и buckets.
- `training/history_snapshot.npz` сохраняет фиксированную 134-недельную историю, 8 789 пар и ID, используемые при обучении. `training/final_raw_components.npz` — кэш прогнозов исходного запуска; его нельзя использовать для новых входов.
- `app/inference.py` умеет пересчитать LightGBM и рекурсивные прогнозы, `app/v8.py` строит финальные признаки, `app/catboost_inference.py` применяет две финальные модели. Но `prepare_features` жёстко загружает фиксированный snapshot, а без `--recompute-base` ещё и кэш. Функции загрузки входных CSV → полноценный Signature `Dataset` в пакете нет.
- Порядок и структура модели сохранены; полный корректный ETL новых CSV в тот же `Dataset` и независимая таблица совместимости всех категориальных ID с произвольными выгрузками не реализованы. Замена словарей данными upload небезопасна.

### MOE

- В соседнем пакете присутствуют шесть обученных файлов (`models_final/*`) и код обучения/feature engineering.
- Переданные `data/history.npz` и `final_expert_predictions.npz` — фиксированные данные и выходы replay. Для пользовательского ввода построитель `Panel`/`FeatureBuilder` и полный динамический путь от новых строк до `predict_experts`/`predict_meta` не интегрированы в ForeStock.
- Совместимость MOE с новыми датами и товарами не установлена. В текущий API этот вариант не добавлен.

## Текущие контракты и ограничения

- Java backend: `POST /predict` синхронно принимает multipart `sales`, `stock`; проверяет обязательные поля/минимальную историю, отрезает данные до последних 52 недель, сохраняет файлы и зовёт ML. ML v7.4, однако, требует свой фиксированный universe и окно 134 недель; Java-предварительная проверка не заменяет его валидацию.
- ML: `POST /v1/predict` синхронно принимает `sales`, `stock`, вариант v7.4, фильтры и недели горизонта. При заданном ключе требует `X-API-Key`. Дополнительно принимает query `cutoff_date`; поддерживается только `2026-07-26`.
- Frontend: Spring Boot/Thymeleaf; он передаёт оба файла backend. В коде репозитория нет React frontend.
- Ежедневные stock-дубли агрегируются суммой по `(date, warehouse_name, article)`. Отрицательные stock допустимы, ноль не запрещает продажу. Неизвестные артикулы и склады отклоняются.
- `discount_sum=null` сейчас не принимается как конечное число: сервис возвращает ошибку, а не трактует null как ноль. Это безопасный отказ, но не полная реализация семантики null из задания.
- Отдельные job-папки и worker очередь не реализованы. Временные файлы запроса изолированы, а расчёт сериализован lock-ом внутри одного процесса; это не заменяет требуемую изоляцию и параллельные jobs.

## Оставшиеся блокеры для заявленной цели

1. Построить Signature `NormalizedHistory`/`Dataset` из двух сырых CSV, сохранив все сигналы департамент/город/категория/характеристика и точную семантику логарифмированных сумм.
2. Доказать parity на оригинальном `hakaton.zip` и получить golden delta `<=1e-3` по ключам. ZIP отсутствует в доступном каталоге; без него pass объявить нельзя.
3. Выполнить изолированный dynamic path, сравнить ключи и выход с эталоном, а также data-dependence, leakage, stock duplicate и negative tests.
4. Реализовать Java jobs API/персистентный статус/result/download и UI, который показывает именно результат текущего job.
5. Отдельно спроектировать и валидировать произвольные cutoff, short history, cold start и новые каталоги. Старые веса для них не подтверждены.
6. Только после Signature parity решать, имеет ли смысл интегрировать MOE; её frozen replay нельзя считать dynamic inference.

Следовательно, текущий сервис можно описывать только как ограниченный rolling inference v7.4 для известной сетки на исходном cutoff. Он не является реализацией полного требования Signature v8.1 из `CODEX_FORESTOCK_DYNAMIC_INFERENCE_TASK.md`.
