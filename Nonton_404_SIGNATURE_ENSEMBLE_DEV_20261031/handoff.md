# Handoff — Nonton v8.1 CatBoost, обученная модель и интеграция в ForeStock

**Дата пакета:** 31.10.2026  
**Статус:** подтверждённый воспроизводимый **frozen inference** на девять конкурсных недель; модельные веса включены. Динамический `POST /predict` по новым CSV в этом релизе **не реализован**.  
**Цель передачи:** дать разработчикам полную исполняемую цепочку модели v8.1 CatBoost, подготовленные веса, контрольный прогноз, обучающий код для двух CatBoost-голов и чёткое задание для реального онлайн-инференса.

## 1. Что было нужно и что именно передаётся

Задача конкурса: недельный прогноз `quantity` по ключу `week, warehouse_name, article` для 9 понедельников с **27.07.2026 по 21.09.2026**, каждый период понедельник–воскресенье. Итого при полном наборе 11 складов × 799 артикулов × 9 недель: **79 101** строка. В обучении и признаках запрещены данные позднее **26.07.2026**. Обновлённое ТЗ имеет приоритет перед устаревшим первоначальным вариантом «64 дня».

Выбранная модель — **v8.1 CatBoost**, соответствующая отправке `прогноз_5` в предыдущей партии команды 404. Это не CatBoost, обученная только на исходных строках `sales`: она использует **39 сохранённых LightGBM-моделей v7.4 как базовый ансамбль**, а затем две CatBoost-модели как отдельные головы решения о продаже и количестве.

В пакете:

- `models/base/` — **39 LightGBM-моделей** и `schema.json` исходного ансамбля;
- `models/catboost/catboost_prob.cbm` — обученный бинарный CatBoost (`quantity > 0`);
- `models/catboost/catboost_logquantity.cbm` — обученный CatBoostRegressor для `log1p(quantity)`;
- `training/history_snapshot.npz` — историческая агрегированная матрица, категории, остатки и другие признаки для frozen-прогноза;
- `training/final_raw_components.npz` — кеш результатов тех же 39 базовых моделей на конкурсной сетке;
- `training/oof/` — семь исторических out-of-fold прогнозов, необходимые для повторного обучения двух CatBoost-моделей;
- `app/` — базовые фичи, построение прогнозов и CatBoost-инференс;
- `forecasts/v81_catboost.csv` — **эталонный прогноз 79 101 строка**, воспроизведённый из реальных моделей;
- `docs/model_schema.json`, `manifest.json`, `tests/` — схема признаков, SHA-256 и тесты;
- `app/api.py`, Docker/PowerShell и пример Java-клиента — референсное чтение фиксированного прогноза по HTTP.

## 2. ML-архитектура, последовательность

```text
Исходная история sales + stock  (при первоначальном обучении)
    └─ обработка дат, недель, суммирование stock-дублей, агрегация продаж
       по warehouse × article; срез history <= 2026-07-26
        └─ [39 обученных LightGBM v7.4]
           ├─ global Tweedie + global Poisson
           ├─ 11 отдельных warehouse-моделей
           ├─ 24 групповые warehouse × category1-модели
           └─ recursive Tweedie + recursive Poisson
           → global_raw, m5lite_raw, hybrid_raw
              └─ [62 признака для каждого warehouse × article × horizon]
                 ├─ прогнозы базовой группы + их разногласие
                 ├─ лаги 4/13/26/52 недель, активность пары
                 ├─ динамика склада и склада × категории 4/13/26/52
                 ├─ stock на конец разрешённой истории, категории
                 └─ только известные заранее календарные признаки
                    ├─ CatBoostClassifier → P(quantity > 0)
                    └─ CatBoostRegressor → log1p(quantity) → expm1
                         └─ осторожное смешивание объёма с hybrid_raw
                             └─ порог вероятности 0.53
                                → quantity >= 1 либо 0
                                   → 79 101 строка CSV
```

**Почему 39, а не 42:** v8.1 CatBoost использует 39 базовых моделей и **2 собственных CatBoost-головы**. Три LightGBM-головы модели v8 (`presence`, `conditional`, `direct`) для исполнения этого конкретного CatBoost-кандидата **не нужны**. Они не включены, чтобы исключить архитектурную путаницу.

**Параметры CatBoost:** 350 итераций, depth 6, learning_rate 0.045, l2_leaf_reg 9, Logloss для вероятности, RMSE для логарифма количества, random_seed 403 и 404. Обучение CatBoost выполнялось на **семи строго исторических OOF-окнах**. Базовые модели не обучались на будущих конкурсных целях.

**Точная формула постобработки:**

```python
prob = catboost_prob.predict_proba(features)[:, 1]
amount = max(expm1(catboost_logquantity.predict(features)), 0)
base = max(hybrid_raw, 0)
ratio = clip((amount + 0.25) / (max(base, 0.5) + 0.25), 0.6, 1.8)
quantity = max(base, 0.5) * (1 + 0.50 * (ratio - 1))
prediction = max(quantity, 1.0) if prob >= 0.53 else 0.0
```

**Значение ratio ограничивается** во избежание нестабильной коррекции объёма. Это выбранный по forward-валидации кандидат `catboost_T0.53_B0.50_R0.000` (не CatBoost вместо всего ансамбля). `R=0` означает отсутствие дополнительной пороговой поправки по активности.

## 3. Данные и контракт

**Вход для frozen-inference:** включённый `history_snapshot.npz`, модели и кеш исходных прогнозов; `hakaton.zip` не требуется. История заканчивается 26.07.2026.

**Выход:** CSV ровно с колонками:

```csv
week,warehouse_name,article,quantity
2026-07-27,warehouse_name_0,char_article_0,0
...
```

Предсказание вещественное, неотрицательное; округлять и приводить к `int` в Java-сервисе нельзя без отдельного согласования и повторной проверки метрик. Сохранить исходные нули; не заменять пропуски тихо. Важен точный набор ключей, а не только число строк. Все 9 недель составляют 27.07—27.09.2026 включительно; поле `week` хранит **понедельник начала** недели.

**Первоначальная история (для динамической версии):**
- `sales`: `date,composite_division,cities_name,warehouse_name,category_lvl_1,category_lvl_2,category_lvl_3,article,characteristic,quantity,sales_sum,discount_sum`;
- `stock`: `date,warehouse_name,article,stock` — в сыром архиве именно `article`, хотя первоначальное ТЗ иногда называет его `char_article`;
- дубликаты `stock` по дате, складу, артикулу **суммируются**, даже одинаковые строки; `stock` — остаток **на начало дня**; отрицательные остатки допустимы;
- `discount_sum=null` означает отсутствие скидки. `sales_sum` и `discount_sum` логарифмированы; при денежной агрегации учитывать обратное преобразование, не воспринимать числа как реальные цены;
- состав `composite_division` — департаменты, это **не доказанный** онлайн/офлайн-канал.

**Критическая граница:** релиз не перестраивает признаки из произвольных файлов пользователя и не сдвигает девятинедельный горизонт. Исторический snapshot нельзя использовать как будто он подходит для нового `sales.csv`. Для динамического `POST /predict` нужен отдельный ETL/сборщик Dataset, пересчёт всех рекурсивных 39 моделей, сборка 62 признаков по последней доступной неделе, корректное определение горизонта и повторная проверка контракта.

## 4. Запуск (Windows 10/11, Python 3.11)

Распаковать ZIP, открыть PowerShell **в корне** папки проекта:

```powershell
powershell -ExecutionPolicy Bypass -File .\install_windows.ps1
powershell -ExecutionPolicy Bypass -File .\verify_windows.ps1
```

Вторая команда строит прогноз **из всех 39 LightGBM + 2 CatBoost** и сверяет с `forecasts/v81_catboost.csv`. Доступен более быстрый режим с сохранённым кешем базовых прогнозов:

```powershell
.\.venv\Scripts\python.exe -m app.catboost_inference --verify
.\.venv\Scripts\python.exe -m app.catboost_inference --out .\new_replay.csv
```

Для локального read-only API:

```powershell
$env:NONTON_API_KEY="REPLACE_WITH_LONG_RANDOM_SECRET"
powershell -ExecutionPolicy Bypass -File .\start_api_windows.ps1
```

Проверка после запуска: `GET http://127.0.0.1:8080/healthz`, Swagger `http://127.0.0.1:8080/docs`. Защищённые маршруты требуют HTTP-заголовок `X-API-Key`:

- `GET /v1/model` — версия, срок действия и число моделей;
- `GET /v1/forecasts?week=2026-07-27&warehouse_name=warehouse_name_0&article=char_article_0` — отфильтрованный прогноз;
- `GET /v1/export.csv` — полный эталонный CSV.

В Docker:

```bash
export NONTON_API_KEY='REPLACE_WITH_LONG_RANDOM_SECRET'
docker compose up --build -d
```

В `docker-compose.yml` порт опубликован только на `127.0.0.1:8080`; внешние запросы направлять через аутентифицированный reverse proxy. **Сборка Docker в этой среде не проверена**, Python inference проверен.

## 5. Переобучение модели

Только **двух CatBoost-голов**, используя семь уже включённых OOF-окон:

```powershell
.\.venv\Scripts\python.exe -m app.retrain_catboost --iterations 350 --threads 8 --out .\refitted_catboost
```

Новые `.cbm` будут в отдельной папке. Скрипт **не заменит** проверенные модели в `models/catboost/`. Чтобы получить новые обучающие OOF для будущих периодов, необходимо повторно обучить 39 базовых LightGBM с временным разбиением и корректным cutoff; один лишь `retrain_catboost` не превращает систему в универсальную прогнозную модель. Переобучать CatBoost на данных конкурсного периода запрещено, если речь о честном воспроизведении конкурсной модели.

## 6. Качество и ограничения

Официальный лидерборд на момент последних доступных команде данных: у `прогноз_5` / v8.1 CatBoost `Score 0.504`, `SMAPE ≈62.342%`, `WAPE ≈49.557%`, `RMSE ≈4.125`, `Bias ≈87.683%`, `RMSLE ≈0.5407`. Он лучше остальных четырёх первых отправок команды 404 **по Score**, но уступал лидерам. Эти показатели относятся к скрытому конкурсному тесту; значения локального CV несопоставимы по шкале.

Модель CatBoost была выбрана из 40 политик своего семейства по пяти расширяющимся историческим периодам, с использованием семи ранних OOF-окон для warm-up и final fitting. `results/candidate_ranking.csv` из полного прогона включён как `research/candidate_ranking_120.csv`. Оптимизация Score по rank на скрытых данных возможна только у организаторов; локальная `mean_relative` — не официальный score.

**Известные риски:**
1. Модель и код инференса привязаны к **фиксированной исторической сетке и фиксированным 9 неделям**.
2. Скрытые ответы конкурса неизвестны, повторить официальный Score локально нельзя.
3. Базовые признаки части департаментов сжаты в `OTHER` по ранней истории; поздние бизнес-режимы могут переноситься плохо.
4. Базовая архитектура часто недопрогнозирует суммарный объём и недостаточно меняет отдельные SKU между неделями.
5. В составе пакета есть агрегированная история продаж — **не публиковать архив открыто**, хранить как бизнес-данные.
6. Реальный `POST /predict` должен принимать **sales + stock** и не обучать модель на каждом HTTP-запросе; без замены frozen-snapshot это будет вводить пользователя в заблуждение.

## 7. Задачи backend, ML и frontend

**ML:** выделить чистый интерфейс `ForecastModel.predict(sales, stock, cutoff) -> DataFrame`, добавить `Dataset.from_csv` с идемпотентной агрегацией и строгой проверкой временной доступности, затем протестировать с историческим origin. Проверить feature parity и численную воспроизводимость, прежде чем менять 41 модель.

**Backend (Java 21 / Spring Boot):** реализовать приём двух больших CSV (streaming upload, отдельные лимиты и timeouts), async job + job ID, статусы `queued/running/completed/failed`, хранение истории и выходного CSV, проксирование Python ML worker по HTTP, авторизация и аудит. Для интеграции уже готовых прогнозов — использовать `GET /v1/forecasts` или импорт CSV в PostgreSQL.

**Frontend ForeStock:** экран «Новый прогноз» должен отличать **загружен/проверен**, **идёт прогнозирование**, **завершено**, **ошибка**. Сейчас read-only API не создаёт новую задачу из CSV. Графики `historical + predicted` требуют нормализации единиц (недели, не дни), явного выбора версии и корректной обработки пустой истории.

## 8. Проверено в этом релизе

- Все 39 LightGBM и 2 CatBoost файла присутствуют.
- Код на Python 3.11+-совместимом синтаксисе, схема из 62 признаков совпадает с обучением.
- На **79 101** ключе воспроизведение из **39 базовых моделей + 2 CatBoost** совпало с исходным CSV: максимальное абсолютное расхождение **4.885e-06 единицы**.
- Использование кеша базовых прогнозов даёт тот же результат.
- `manifest.json` проверяет SHA-256 файл-за-файлом; результаты API smoke-test описаны в `tests`.
